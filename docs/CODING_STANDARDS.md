# Aether 编码与工程规范

迁移来源：`设计2.0.md` §4（C17 语言与工程）、§8–10（日志、错误、内存与资源）、§11（编码与同步要求）、§14（技术选型与依赖）、§17–18（测试与开发评审）。本文件承接这些章节的详细工程规则。

## 1. 范围、状态与规则强度

当前仓库处于文档阶段，尚无源码、CMake 工程、测试或 CI。本文件约束后续实现与审查，不表示示例接口、工具链或候选依赖已经实现、选定或验证。

- “必须”“禁止”为硬约束；“应”“建议”“优先”为默认方向，偏离须说明原因；候选方案不是已接受选型。
- 本文件维护编码和工程细则；分层、源码依赖、线程拓扑及 UI/Backend 边界以 [ARCHITECTURE.md](ARCHITECTURE.md) 为准。
- 公共状态码集合、生命周期、所有权、线程安全声明和异步接口语义以 [INTERFACE_CONTRACTS.md](INTERFACE_CONTRACTS.md) 为准；本文件不复制其类型定义，不建立另一套 API/ABI。
- 工作入口、任务交付与规范变更流程见 [AGENTS.md](../AGENTS.md)。重大架构、公共契约、安全或依赖决策须先确认并记录 ADR，不能将候选方案写成已接受决策。

## 2. C17、构建与可移植性

### 2.1 语言与自研边界

Aether 自研核心代码必须使用 ISO C17。禁止以 C++、Objective-C 实现核心业务，禁止将 C++ 类库作为核心架构依赖，禁止使用 C++ 编译器特性或以 GCC/Clang 私有扩展作为公共接口基础。

允许 C17 标准特性、跨平台 C 库及平台原生 API 的 C 接口。第三方 Runtime 可以使用其他语言。UI 框架、平台 API 或第三方库所需的语言绑定必须隔离在独立边界内，不得侵入 Core。

C17 是对 C11 的修订，不是引入新语言范式。使用 C17 不意味着所有可选标准设施都在 Windows、macOS、Linux 的目标工具链中可用，也不意味着已选定最低编译器版本。

### 2.2 CMake 与警告策略

CMake 必须显式设置：

- `CMAKE_C_STANDARD` 为 `17`。
- `CMAKE_C_STANDARD_REQUIRED` 为 `ON`。
- `CMAKE_C_EXTENSIONS` 为 `OFF`。
- 自研核心工程以 C 语言构建（对应 `project(Aether LANGUAGES C)` 的声明意图）；不能用 C++ 模式绕过 C 编译问题。必要平台绑定在独立边界配置。

以上是配置要求，不是当前仓库的可执行工程或构建命令。

自研代码必须启用严格警告。GCC / Clang 建议列表完整保留如下，实际配置时按目标编译器支持情况核实：

```text
-Wall
-Wextra
-Wpedantic
-Wconversion
-Wshadow
-Wstrict-prototypes
-Wmissing-prototypes
-Wformat=2
-Wundef
-Werror
```

MSVC 应采用等价的严格警告策略，具体选项在真实工具链配置时确定。不得通过关闭检查或无根据的强制类型转换掩盖自研代码问题。第三方库的警告策略与自研代码分开管理，不能因第三方告警整体降低自研要求。

### 2.3 可移植性建议

以下是面向跨平台实现的明确建议，不是已经完成的平台验证结论：

- 不使用变长数组（VLA）或 Annex K 的可选边界检查接口作为可移植实现基础；选择容量明确、目标平台支持的实现。
- 不假定 C 标准线程、原子操作或其他可选设施在所有目标工具链上具有同等可用性。采用前核实支持与语义，平台差异通过 Platform 边界处理，不能散落在 Core 或应用服务中。
- 不把 `volatile` 当作线程同步：它不能替代互斥、原子操作或消息传递，也不建立线程间的同步关系。
- 不假定指针宽度、整数宽度或隐式转换在各平台一致；容量、长度、格式化参数与类型转换须接受严格警告审查。

最低工具链版本、平台支持矩阵及各质量工具可用配置须待真实工程建立时明确，不在本文伪造验证结果。

## 3. 命名、头文件与组合设计

### 3.1 命名

| 对象 | 规范 | 示例（仅命名示意） |
| --- | --- | --- |
| 类型、结构体、枚举 | `PascalCase` | `AetherRuntime`、`AetherSession`、`AetherRuntimeState` |
| 公共函数 | `snake_case`，统一 `aether_` 前缀 | `aether_runtime_start` |
| 变量 | `snake_case` | `runtime_id` |
| 宏 | `UPPER_SNAKE_CASE` | `AETHER_STATUS_OK` |
| 私有函数 | `static`、`snake_case` | `runtime_cleanup` |
| 文件 | `snake_case.c` / `snake_case.h` | `runtime_manager.c` |

模块私有函数不得暴露到公共头文件。

### 3.2 头文件

每个模块必须有独立公开头文件，只暴露必要接口，优先使用不透明结构体。禁止：

- 暴露内部实现结构，或将私有函数声明为公共 API。
- 在头文件中定义大量全局变量。
- 在公共头文件中包含不必要的依赖。
- 用头文件循环依赖解决模块耦合。

DTO 与领域内部对象必须分离；不得以方便调用为由公开私有结构。公共接口的具体定义与兼容性规则由接口专题维护。

### 3.3 组合与函数表

推荐封装、抽象、多态、组合与接口；优先组合而非继承模拟。函数表用于真实多态边界，不为每个对象机械增加抽象。避免过深的继承模拟，不允许通过随意强制类型转换模拟继承，不得把全部能力堆入一个 Manager。

采用函数表时，必须明确函数表及 `context` 的生命周期和创建、释放责任；函数表在对象使用期间必须有效；调用前必须校验函数指针是否为空。具体所有权和生命周期契约见接口专题，不能把函数表示意当成已发布 C ABI。

### 3.4 文件长度与单一职责

- **每个手写代码文件最多 500 行。** 适用于自研 `.c`、`.h`、测试代码及开发/构建脚本；不是每个文件应尽量写满的目标。Markdown 文档不按代码文件统计。
- 按物理行计数：包含空行、注释、预处理指令和许可证头；CRLF 与 LF 都算一次换行，末尾无换行符的非空行也计一行。不得只统计非空代码行来绕过上限。
- **超过 300 行须审查职责，超过 500 行不得交付。** 修改前检查现有行数与职责，预计越界时先按职责拆分。测试代码同样受限，不能沿用参考规范对测试的宽泛豁免。
- 每个文件应有一个能用一句话描述的主要职责；解析、领域状态转换、持久化、进程控制和 UI 呈现不能因“同属一个功能”就全部塞进同一文件。即使不足 500 行，职责混杂也必须拆分。
- 按领域操作、数据转换、协议解析、请求编排等真实边界拆分。禁止机械生成 `part1.c`/`part2.c`、移动成另一个大文件、删掉必要注释、挤压空行、多语句合行、巨型宏或 `#include` 实现片段来隐藏规模。
- 拆分须保留唯一状态机、DTO/错误契约来源、事务协调入口和资源所有者；不能为了跨文件调用扩大公共 API。文件内辅助函数保持 `static`，跨文件内部接口放在必要的私有头文件中。
- 第三方原样源码、可重生成代码及纯数据资源不机械套用手写代码上限，但必须可识别来源、生成方式和路径范围。手写业务逻辑不能移入这些区域或伪称生成代码；手写测试 fixture 的逻辑仍受限。
- 函数保持单一职责；超过约 60 个物理行应审查是否混入多个阶段、过深嵌套或多个资源职责。这是审查信号，不是机械切函数的硬上限；不得把完整状态机拆成难以追踪的碎片。

### 3.5 C 源码行宽与排版

**排版目标为 80 列，常规代码行硬上限为 100 列。** 适用于手写 C 源码与头文件（含测试）中的声明、表达式、宏和注释。80 列以内优先；81–100 列在避免不自然断行时可用，超过 100 列必须合理换行或符合下述明确例外。

- C 源码使用 4 个空格缩进，不使用 Tab 缩进或对齐；不保留行尾空白。一个逻辑语句单独一行，`for` 头部的分号不属于多语句合行。
- “列”是显示宽度，不是 UTF-8 字节数：ASCII 为 1 列，中文等宽字符通常为 2 列，组合附加符不另占列；检查工具的 Unicode 宽度规则须固定。换行符不计宽度。
- 参数、条件和初始化列表在语义边界断行，不为缩短行宽滥用缩写、嵌套三元表达式或宏。过深缩进先审查控制流，不能只靠换行掩盖职责问题。
- 不可拆分的 URL、需保持可检索的完整诊断字符串、原样协议/测试数据可申请窄范围行宽例外；能通过自然换行或 C 相邻字符串字面量保持清晰的内容优先换行。不得对整个业务文件关闭限制。
- 行宽例外须记录规则、文件及稳定定位（符号或内容类型）、原因、风险、替代检查和失效条件，并在交付中报告；例外不是 500 行上限的豁免，AI 不得自行放宽文件长度。
- 以后选用 formatter 时配置对应行宽目标，并配套检查 100 列上限及已记录例外；formatter 的排版目标不等于硬限制检查。当前未选定工具版本、未建立配置，不宣称自动检查已经落地。

GitHub 和 ISO C17 均未规定统一源码行宽。本项目取值是可读性与长 API 名称之间的项目约定，不是“GitHub 最大允许值”。参考：[curl 明确限制 79 列](https://curl.se/dev/code-style.html)、[Linux 优先 80 列并允许可读性例外](https://docs.kernel.org/process/coding-style.html)、[Git 尽量不超过 80 字符](https://github.com/git/git/blob/master/Documentation/CodingGuidelines)。仅借鉴行宽取舍，不照搬这些项目的语言版本、缩进或其他约定。

## 4. 日志

### 4.1 统一等级与接口

日志是基础设施能力，必须从项目早期统一建设、统一封装，并支持按 Trace ID 检索分层调用链。业务模块不得自行实现不同日志格式，不得建立平行追踪框架，也不得用 `printf` 代替业务日志。当前尚无实现，本节规定后续工程要求。

| 等级 | 用途 |
| --- | --- |
| TRACE | 有界、脱敏的协议元数据、事件归约和底层细节，不等于原始报文转储 |
| DEBUG | 边界操作入口、出口、耗时和有限摘要 |
| INFO | 顶层操作开始/完成、正常业务流程与关键生命周期 |
| WARN | 取消、超时、业务拒绝及其他可恢复异常 |
| ERROR | 非预期操作失败、进程故障、清理失败等需要诊断的错误 |
| FATAL | 系统无法继续运行 |

日志等级不是错误处理流程；记录 FATAL 不授权以 `abort` 代替清理与错误传播。

### 4.2 结构化字段与安全

边界日志必须结构化；全部公共字段及适用条件统一维护于 [INTERFACE_CONTRACTS.md](INTERFACE_CONTRACTS.md) §13.2。输出可为稳定键值文本或结构化记录，但不能将字段全塞进 `message`，新增输出后端不得改变字段语义。

字段按契约适用性填写，下列安全与关联要求不能因“选填”而放宽：

- 日志必须带模块标识；操作边界及重要异步路径必须携带 TraceContext 中的追踪标识，相关业务 ID 按需追加，`request_id` 不能代替 `trace_id`。
- Runtime 相关日志应包含 `runtime_id`；Session 相关日志应包含 `session_id`。
- 敏感信息必须脱敏，禁止写入 API Key、Token、密码。
- 不允许在高频循环中无节制输出 DEBUG 日志。
- 不允许吞错，也不允许重复记录同一错误；错误记录责任与传播层级应明确。
- 禁止记录 Authorization/Cookie、带凭据 URL；默认不记录用户输入、模型输出、Skills 正文和工具参数原文，优先记录关联 ID、错误码、计数、耗时与大小。诊断信息及公开错误须排除凭据、敏感路径、SQL 参数和上游敏感原文。

正式日志 API 发布前必须定义结构化字段类型、格式化规则和字段生命周期，不能从示意调用猜测参数或内存约定。

### 4.3 日志与业务事件

日志用于诊断，业务事件用于驱动系统行为，两者必须分离。一个业务操作可以同时发布业务事件和写日志，但禁止通过解析日志实现业务事件或系统状态转换。

### 4.4 等级过滤与设置

- 严重性顺序为 TRACE < DEBUG < INFO < WARN < ERROR < FATAL，采用阈值语义：选定级别及更严重的记录可输出。默认 INFO，保留 Aether 的 FATAL，不把正常用户取消当作 ERROR；取消后的清理失败单独记录 ERROR。
- 支持运行时切换级别、用户选择持久化及重启恢复。有效级别为`--log-level` > `AETHER_LOG_LEVEL` > 持久化用户设置 > INFO，仅接受不区分ASCII大小写的完整六级词；非法CLI拒绝启动参数，非法ENV明确忽略并提示健康故障，非法持久值按INFO运行并提示损坏、不覆盖磁盘。设置API非法值拒绝；保存失败保持旧偏好/有效值。
- 临时覆盖不写回持久化设置。UI 须同时显示有效级别与来源；存在覆盖时，保存用户偏好不应伪称已改变有效值，应说明覆盖仍生效。保存失败必须报告，不能声称重启会恢复；无效设置须有显式诊断和已定义处理规则，不静默猜测。
- 设置只影响未来记录，不补回已过滤的历史日志。运行中从 INFO 切到 DEBUG 可能看到有出口无入口的 span，应提示捕获不完整；不会为补齐记录伪造过去事件或无界缓存历史。
- INFO 保留顶层生命周期和最终结果，不被普通方法入口淹没；DEBUG 才提供正常边界入口/出口全貌。完整链路承诺限于采集期间等级允许且输出正常的 Aether 可观测边界，不包含任意第三方内部实现。

### 4.5 C17 操作生命周期与传播

TraceContext、span 字段、父子关系、外部传播和终态语义以 [接口契约](INTERFACE_CONTRACTS.md) §13 为准。实现时必须：

- 给有副作用、跨边界、可能失败或明显耗时的公共操作提供统一入口和终结记录；纯 getter、紧密循环和普通内部 helper 不机械创建 span。操作名稳定且可定位实际函数，各层只记录自己的边界。
- 跨线程、任务队列、计时器、回调、进程读写和事件分发显式携带上下文；不得用全局“当前请求”、共享可变父上下文或线程 ID 猜测归属。
- 同步操作覆盖所有返回分支，异步操作由实际完成者终结；可用普通 C 辅助函数和清理出口，不依赖 Rust guard、C++ RAII、私有 cleanup 扩展或巨型宏模拟析构。
- 任务所有者在正常关闭/销毁时检查操作是否结束，按接口契约报告 `unfinished`；C 没有 `Drop` 自动兜底，不用编译器扩展模拟，也不为此建立扫描所有对象的全局注册表。覆盖早退、重复关闭和被取消任务的验证不可省略。
- 耗时用单调时钟，墙钟用于展示时间；记录成功、失败、取消、超时及后续清理。取消被受理、等待超时、实际工作停止、资源已关闭是不同事实，不混成一条成功出口。
- 每个边界记录自己的结果，根因详细诊断只由负责边界记录一次；传播层不重复输出同一完整错误。并发竞争不能造成一个 span 先失败后成功，日志写入失败不能改变业务返回值。

### 4.6 性能、脱敏与日志存储

- 先判断级别是否启用，再构造昂贵字段、格式化或分配缓冲区；关闭的 DEBUG/TRACE 不得触发可避免的序列化、字符串复制或堆分配。业务必要的关联上下文仍须保留，不因日志级别关闭而丢失请求身份。
- 字段按类型与长度写入，使用有界缓冲区或受控队列；异步写入不得引用栈内字段。明确单条大小、队列容量、溢出策略与丢弃统计；禁止为保证日志而无限分配或阻塞 UI。
- 所有等级都遵守 §4.2 脱敏要求。TRACE 只增加允许的协议类别、字节数、状态等元数据；禁止直接转储完整 prompt、文件正文、Base64 附件、凭据、原始敏感 URL 或无界响应。记录前转义换行和控制字符，避免外部输入伪造记录。
- 字段名是“摘要”不代表安全：完整 `file_path` 可能暴露用户或项目身份，`content_hash` 可能关联私有内容。默认不记录，只有明确诊断需求、范围和隐私评估后才可纳入允许字段；优先使用目标类别、字节数或不敏感内部 ID。
- 高频流式 Delta 和循环诊断应汇总、限频或按声明策略采集；不得静默丢弃后仍宣称完整。普通方法入口退出与关键终态的优先级/丢弃规则须明确，丢失可观察；不能以逐 token 日志替代业务事件。
- 文件写入、轮转、保留、flush/关闭和有界读取属于统一日志基础设施。实现前必须确定路径、访问权限、单文件/总量上限、保留期限与异常退出时的持久性边界；不承诺崩溃前最后记录必然落盘。
- 磁盘满、不可写或队列溢出时，通过有界、非递归的诊断状态暴露故障，不无限重试，也不递归调用故障 logger。业务错误传播仍继续，安全审计若要求失败关闭须另行制定契约，不能把诊断日志当作合规审计保障。
- 日志基础设施只提供等级、记录句柄、上下文/操作辅助、字段写入、脱敏、输出和读取能力；不内置 UI、产品偏好、业务实体或数据库 Schema。复用标准库、Platform 和已选依赖，不因该要求引入通用 tracing 框架或远端采集系统。
- DEC-10本地输出选择与细则见[ADR-0010](adr/0010-local-diagnostics.md)：严格UTF-8 JSONL/yyjson 0.13.0，生产者过滤后一次编码、固定arena，队列持编码字节，writer不重复编码；无堆回退。16KiB记录、1024条/4MiB队列（重要预留128条/512KiB）、单文件8MiB/实例64MiB/用户256MiB、14天最长保留。数值由DEC-11统一入口引用，不是吞吐或保留SLA。
- 输出为每用户私有状态目录：Windows LOCALAPPDATA/Aether/logs、Linux XDG_STATE_HOME或HOME/.local/state下aether/logs、macOS Library/Logs/Aether。POSIX目录0700/文件0600，Windows仅当前用户及SYSTEM受保护DACL；验证所有者、链接/重解析点，实例锁与根配额串行管理，不能清理的文件仍计占用。故障不回落公开目录或stderr；不是防同用户恶意进程的审计设施。
- writer短写受检，64KiB/1秒批写；停止生产后drain截止1秒，超时保留活跃资源责任并报告pending。flush仅到OS缓存，不承诺fsync/断电最后记录。持久错误封存半行文件并停输出，显式重试或下次启动才重开；所有故障通过有界健康状态报告，计数饱和不回绕。

### 4.7 产品诊断与实现顺序

Backend 必须提供按 `trace_id` 检索及按 operation/layer/component/level 筛选的受控诊断接口，前端支持复制 Trace ID、错误提示中的诊断 ID、查看时间与耗时。默认显示 INFO 及更严重记录（包括 FATAL）；DEBUG/TRACE 可选择采集并查看，界面展开不能恢复从未采集的内容。查询应有分页/数量限制，提示日志已轮转、被过滤或可能缺失，不伪造“没有错误”的结论。

用户偏好及其持久化归配置/应用服务，日志基础设施只接收有效级别；前端不直接读日志文件或绕过 Backend。诊断 ID 不授予读取任意 Workspace 日志的权限。

实施前调查真实日志初始化、过滤器、输出路径、轮转/查看方式、请求入口、线程队列、错误取消路径、公开接口及全部调用方；复用现有设施，已有输出路径不得被无说明替换。当前不存在实现，应与工程基础一起建立，不编造迁移对象。

落地顺序为：统一日志接口与字段 → root/child 上下文及跨异步传播 → 各实际边界生命周期 → 等级切换、持久化和临时覆盖 → Backend 检索及 UI 诊断 → 行为验收。OpenTelemetry/OTLP 等远端后端只在真实需求出现并评估后决策；不为未来复用预建额外框架。

### 4.8 实际行为验收

下表是后续日志功能交付的验收要求，不是本轮文档修改已执行的软件测试。必须运行真实操作，并从实际输出/查询结果观察关联关系，不能只断言源码有字符串或 logger 被调用。

| 场景 | 必须观察到的结果 |
| --- | --- |
| 正常操作，DEBUG 采集 | 同一 Trace ID 下入口、应用服务、实际存储/Adapter 等边界的父子关系、入口/出口及耗时；只覆盖真实存在的层 |
| 并发请求及跨线程/队列/回调 | 各 root 不串 ID，子 span 不共用可变状态；任务脱离提交栈后上下文仍有效 |
| 失败、取消、超时与清理 | 稳定错误码定位失败层/函数；每个 span 不出现矛盾终态，后续清理成功/失败可关联，正常取消不是系统 ERROR |
| 等级与配置 | 六级阈值正确；INFO 无普通方法入口洪泛；运行时切换、持久化重启恢复、命令行/环境覆盖优先级及保存失败提示符合规则 |
| 用户诊断 | 从真实错误提示复制 ID，通过 Backend/实际 UI 找到相应记录及层级/耗时，筛选有效；被过滤或轮转记录明确不可恢复 |
| 外部 Runtime | 支持追踪的协议按契约传播；不支持时看到本地外部调用 span 和正确请求映射，无法关联的输出不串给其他请求 |
| 脱敏与日志注入 | 用合成凭据、prompt、文件正文和控制字符触发路径，实际输出无秘密正文且不能伪造记录 |
| 压力与输出故障 | 关闭等级不执行昂贵字段构造，队列/文件有界；磁盘不可写、队列满及关闭中写入不阻塞 UI、不递归日志、不改变业务错误，丢失可见 |
| 请求/响应与未结束操作 | 业务 DTO 不混入追踪/身份元数据；边界限制输入大小，响应保留安全错误码及诊断 ID、不泄漏原文；正常销毁时遗漏终结产生一次 `unfinished` 诊断，不伪报业务完成 |

自动化验证使用可控 Runtime/服务、临时日志目录和合成数据；真实 Adapter 接入及实际 UI 另行验收并注明平台。不得用模拟结果声称外部系统内部追踪已验证。

## 5. 错误传播与清理

### 5.1 显式错误与上下文

错误必须显式返回，具有明确归属，可以向上层传播并保留上下文。必须检查函数返回值，正确释放资源。统一状态码表示错误类别，业务错误码进一步定位具体问题；状态码集合以接口专题为唯一维护处。

调用方按状态码或错误类型分支，不得按错误文案、字符串包含或正则判断类别。跨边界错误转换为公共错误契约，保留必要的脱敏上下文；外部副作用已发出但结果未知时，不得擅自重放操作或伪报成功，重试须有明确契约依据。

每个错误最终应能够定位模块、操作、相关 Runtime、Session、请求以及原始原因。不适用的关联对象不应伪造。禁止：

- 静默忽略错误或忽略返回值。
- 使用 `abort` 代替错误处理，或用 `longjmp` 模拟异常。
- 错误后继续执行不安全逻辑。
- 重复记录同一错误。
- 用 `NULL` 同时表示多种不同错误。
- 只返回通用内部错误而丢失底层原因。

### 5.2 错误对象与清理实现

建议使用统一错误对象承载状态、具体错误码、消息、模块和函数上下文。对象布局不是既定 ABI；正式实现必须解决字符串生命周期，禁止把局部字符串指针保存在长期错误对象中。

可评估的字符串存储方案包括：对象拥有字符串内存、固定长度缓冲区、引用计数的不可变对象、调用方提供缓冲区。这些是备选方案，不代表已选择其中一种。采用错误对象时必须提供配套的创建、复制、释放接口，其具体签名与所有权规则由接口专题承接。

推荐状态码返回与统一清理出口。清理必须依据对象状态和已经成功取得的资源执行：初始化失败应正确回滚，销毁应支持部分初始化；不能简单地释放调用方或其他对象拥有的资源。对同一错误应明确负责记录的层级，底层不应重复记录已经向上传播的同一失败。

## 6. 内存、资源与字符串安全

### 6.1 实现责任

必须遵守显式所有权。每个动态资源的创建、持有、使用、释放、转移及共享责任须落实到接口契约，详见接口专题；推荐“谁申请，谁负责释放，转移通过接口明确表达”。实现和审查必须逐项核对这些责任，不得因指针可访问就推定拥有资源。

必须避免内存泄漏、重复释放、释放后使用、缓冲区溢出、未初始化内存、无效指针和越界访问。所有 `malloc`、`calloc`、`realloc` 必须检查结果；分配失败路径须保留可清理状态并正确回滚。异步持有的数据必须复制或明确转移所有权，不得保存临时指针。

### 6.2 资源取得与释放配对

| 取得资源 | 对应释放责任 |
| --- | --- |
| `malloc` 等分配 | `free` |
| `fopen` | `fclose` |
| Socket | `close` / `closesocket` |
| `CreateProcess` | 关闭相关 Handle，并按进程生命周期契约处理运行状态 |
| libuv Handle（若选用） | `uv_close` 后完成释放，不将发起关闭等同于可立即释放 |
| Thread | Join / Detach，按已声明的生命周期完成资源处理 |
| Mutex | Destroy |
| Database Connection | Close |

不同平台的资源释放函数必须通过 Platform 层统一封装。进程、句柄、线程、订阅等非内存资源同样不得泄漏；取消、失败和销毁路径必须覆盖其清理，不能只审查正常路径。

### 6.3 字符串与缓冲区

字符串必须明确编码、长度、是否以空字符 `\0` 结尾、是否拥有内存、是否允许修改以及有效期；指针是否可为 `NULL` 也须明确，不能与终止符混淆。跨模块传输优先明确长度的字符串视图或 DTO，不得默认借用的字符串可长期保存。

禁止 `strcpy`、`strcat`、`sprintf`。优先容量受控的实现，例如 `snprintf`、先检查长度的 `memcpy`、字符串 Builder 或明确长度的字符串 API。复制前必须检查容量，`snprintf` 必须检查返回值并正确处理截断；“带长度参数”本身不等于安全。

## 7. 并发与异步实现

系统必须采用异步事件驱动设计。架构线程拓扑及队列边界见架构专题；线程数量与执行模型应依据实际负载确定，不应无理由创建大量线程。libuv 是候选基础设施，不是已批准依赖。

### 7.1 UI 与共享状态

- UI 只能在 UI 线程更新；后台事件必须通过 UI Queue 返回。
- 禁止后台线程直接操作 UI 控件，禁止 UI 线程同步等待 Runtime、执行长时间 IO 或直接解析大型数据。
- 每个公共接口必须声明线程安全属性，具体分类及契约要求见接口专题。
- 共享数据必须有明确同步策略；可选互斥锁、读写锁、原子操作、消息队列或事件循环线程约束。
- 优先消息传递与单线程事件循环管理状态，减少共享可变数据。`volatile` 不能替代同步。

### 7.2 异步路径审查

每个异步任务必须考虑成功、失败、超时、取消、重复请求、资源释放、回调线程及对象销毁期间的回调。异步回调不得访问已经释放的对象。

取消是否立即停止、是否终止运行进程、已产生结果是否保留、能否重复取消，以及回调和对象生命周期的具体关系，必须在正式接口中明确；见接口专题。实现不得自行猜测这些语义，也不能仅测试成功回调就认为异步路径完成。

## 9. 测试层次与质量门槛

### 9.1 测试设计

测试是模块设计的一部分，不是开发完成后的附加工作。

| 层次 | 验证目标 |
| --- | --- |
| Unit Test | 模块内部逻辑 |
| Integration Test | 模块之间协作 |
| Contract Test | 接口契约 |
| Adapter Test | Runtime 适配 |
| E2E Test | 完整业务流程 |
| Regression Test | 防止历史问题重现 |

每个核心模块必须有单元测试，重点覆盖正常和错误流程、边界条件、空参数、分配失败、资源释放、状态转换及并发安全。

集成测试重点验证 Backend 与 Core、Core 与 Adapter、Adapter 与 Runtime、Event Bus 与 Frontend、Session 与 Workspace、MCP 与 Tool Registry 的协作。这里描述的是协作验证，不授予违反架构分层的源码依赖。

第三方 Runtime 不能作为单元测试的强依赖，必须支持 Mock Runtime 和 Simulator；开发阶段应优先用它们完成大部分测试。模拟仅用于明确标识的测试与开发场景，不能冒充正式功能；模拟通过不等于真实 Runtime 接入通过，正式 Adapter 必须另行验证实际接入。

永久测试必须断言消费者可观察的行为、边界、不变量或状态转换，不能仅凭函数被调用、参数转发、文件/类型存在、源码包含字符串、程序没有崩溃或数组非空证明正确。修复缺陷应保留失败前/修复后可区分的回归测试；确实不适合自动化时报告原因和实际行为验证证据。单元和常规集成测试使用隔离临时数据及本地可控服务，不读写开发者真实数据、不使用真实凭据或依赖不受控外网；真实 Runtime 验证单独安排并声明环境与副作用。

### 9.2 提交检查与环境边界

代码提交至少执行适用的 CMake 配置、编译、静态检查、单元测试、基础集成测试、内存与资源检查，并验证受影响真实场景。建议在 CI 加入 AddressSanitizer、UndefinedBehaviorSanitizer、ThreadSanitizer（支持的平台）、Valgrind（适用环境）及静态代码分析；工具组合须按平台支持安排，不假定全部工具处处可用。

缺少平台或工具时必须准确说明未验证项及原因，不能宣称跨平台验证完成。禁止删除有价值的断言来通过测试，禁止声称未执行的检查已通过。

当前没有可执行构建或测试命令。工程建立后应从实际 CMake 配置、Presets 和 CI 确定命令，首次成功执行后在 AGENTS 入口记录平台、前置依赖和真实入口。仅文档任务检查引用、章节导航、规则一致性和示例，不运行不存在的构建流程。

交付前必须统计本次新增或实质修改的手写代码文件物理行数，检查超过 300 行文件的职责、500 行上限、C 源码 100 列上限和行宽例外。报告文件路径、行数、职责判断和例外；拆分后运行覆盖受影响调用路径的编译与行为验证。仅统计行数不能证明模块化或行为正确，当前无源码也不能声称源码检查已通过。

## 10. 模块开发与代码评审

### 10.1 开发顺序与模块交付

功能开发依次进行：需求及分析、模块职责确认、架构影响分析、接口设计与评审、实现、单元测试、集成测试、代码审查、文档更新、合并。应先定义或复用接口再实现，不得让实现倒逼其他模块接受未评审契约。

新增模块必须提供：模块说明、职责、公共接口、数据结构、生命周期、依赖关系、错误处理、日志规范、线程安全说明、单元测试。架构与接口内容分别遵守对应专题；变化须同步全部受影响调用方、测试及文档。

只实现当前范围内的完整行为，复用现有能力，不附带无关重构；不得以空函数、TODO、假成功或 Mock 冒充正式实现。

每次变更只服务一个明确的行为目标。修改公开函数、类型、字段、错误码前追踪全部受影响调用方和测试，复用已有定义；不靠兼容别名、默认回退或平行实现掩盖契约冲突。不顺手升级依赖、改数据库格式、扩大权限或增加无需求的线程、缓存、重试和配置项。

格式迁移与行为修改分开处理，不将全仓格式化混入功能变更；只格式化必要范围。缺陷修复先定位根因及共享路径，而非只特判当前报错输入。跨文件拆分保持同一业务行为，不额外复制状态机或修改公共合同。

### 10.2 审查清单

- 分层是否正确，是否出现循环依赖、对具体实现的越界依赖、私有结构泄漏或公共契约破坏？
- 命名、公开头文件、组合及函数表是否符合 §3，是否引入重复代码、巨型 Manager 或不必要抽象？每个手写代码文件是否不超过 500 行、超过 300 行是否完成职责审查，C 行宽是否满足 80 列目标/100 列上限及明确例外？
- C17 配置与严格警告是否满足 §2，是否依赖未经核实的可选设施或私有扩展？
- 所有权与生命周期是否明确，失败、取消、部分初始化和销毁路径是否存在泄漏、重复释放或失效指针？
- 字符串容量、长度、终止符、空值与有效期是否明确，截断和分配失败是否正确处理？
- 共享状态与回调线程是否符合约定，是否阻塞 UI 或存在销毁后的回调访问？
- 错误是否被吞掉、丢失上下文或重复记录，日志是否充分且不泄漏敏感信息？
- 测试是否覆盖对应层次、错误与边界路径，是否将模拟结果误当真实接入结果？
- 依赖是否必要，是否完成版本、许可证、平台、构建、升级和安全评估并隔离调用？
- 接口、调用方、测试及文档是否同步，实际验证与未验证项是否如实报告？

## 11. 实施前必须明确的事项

以下不是预先接受的新设计，而是对应实现或正式接口发布前必须解决的事项：

1. 工程落地：最低编译器与 CMake 版本、平台支持矩阵、可选标准设施可用性、真实配置/构建/测试入口，以及各平台严格警告和检查工具配置。
2. 依赖落地：候选库是否采用、具体版本及依赖清单要求；未评估前不默认全部引入。
3. 日志接口：按 §4 和接口规范 §13 明确 ID 编码/生成、字段容量与所有权、单调时钟、输出后端、队列/轮转/保留上限、故障行为及配置/查询接口；不能重新将已采纳的追踪要求降为可选。
4. 错误接口：错误对象存储方案及创建、复制、释放接口；公共状态码和具体错误码契约由接口专题维护。
5. 并发实现：依据负载确定线程及执行策略；共享状态同步、线程安全声明、取消与销毁期间回调语义须先与接口契约对齐。

这些事项应在实际选型或设计时形成有依据的决定，需要 ADR 的重大决策按 AGENTS 流程确认；不得在当前文档阶段虚构版本、正式函数签名、实现或测试结果。
