# ADR 0003：采纳显式上下文的可追踪分层日志

- 状态：已接受（需求与架构边界，不代表实现完成）
- 记录日期：2026-11-07
- 决策依据：用户要求评估并融入 LumaKit 的 `traceable-logging-requirement.md`，并补充参考 `Rust-LumaKit-日志-请求-响应-异常封装优化建议.md`；评估认为目标适用于 Aether，语言实现方式须转为 C17。
- 当前规则：[架构规范](../../ARCHITECTURE.md) §3.3、[接口契约](../../INTERFACE_CONTRACTS.md) §3.3/§13、[工程规范](../../CODING_STANDARDS.md) §4。
- 替代关系：补充 ADR 0002 的诊断边界，不替代其分层、Runtime 独立性或事件模型。

## 背景

仅统一日志格式和 request_id，不能保证一次用户操作经过应用服务、Runtime Adapter、队列和回调后仍可关联，也不能区分受理、完成、取消和后续资源清理。C17 没有 Rust 的自动析构保证，追踪必须与现有显式所有权、错误传播和异步契约一起设计。

## 决策

采用显式只读 TraceContext、独立 root trace 和父子 span。支持稳定结构化字段、分层入口/终结与耗时、并发隔离、六级过滤、运行时等级设置及持久化/临时覆盖、Backend 受控检索和 UI 诊断 ID。完整链路的范围是采集条件满足时的 Aether 可观测边界，不声称第三方 Runtime 内部可见。

业务 DTO 与请求上下文分离；领域/应用服务不返回产品或传输响应，由实际出口映射稳定错误码、安全提示及诊断 ID。任务所有者负责显式结束 span，正常销毁发现未结束操作时报告诊断，不模拟 Rust Drop 或伪造业务终态。

统一日志基础设施不依赖 UI、业务实体和配置持久化模型。敏感数据在所有级别受控，被过滤的日志不做可避免的昂贵构造，队列/文件有界，写入故障不改变业务结果或导致递归记录。

## 理由与替代方案

仅靠入口日志、线程 ID 或全局当前 trace 无法可靠关联并发异步操作。逐函数或逐 token 打印产生噪声、成本和泄漏风险，选择实际边界记录而非全量拦截。直接复制 Rust guard、泛型结果或反射代理不适用于 C17，也不需要另一套公共框架。

保持普通 C 接口、明确所有者和独立诊断元数据，可以在既有分层内实现目标。外部系统不支持传播时记录本地调用边界及请求映射，而非更改其 prompt 或协议。OpenTelemetry/OTLP 和远端采集不是当前需求的前置条件。

## 影响与风险

后续公开接口、任务/事件信封、日志查询与配置接口需要明确承载方式和生命周期。需验证 ID 并发唯一性、跨线程寿命、取消/超时竞态、未结束操作、等级覆盖、脱敏、输出故障与 UI 查询。级别过滤、轮转、压力丢弃或崩溃可能造成缺失，必须如实展示，不承诺零丢失或日志等同安全审计。

本 ADR 不选定日志库、ID 格式/算法、文件编码、容量数值、线程拓扑、自动堆栈方案或远端后端。具体选型及必要契约仍须有实际证据；当前无源码和运行验证，不能将规范采用报告成日志系统已实现。
