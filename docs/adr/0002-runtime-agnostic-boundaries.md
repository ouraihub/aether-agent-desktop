# ADR 0002：前后端分离与 Runtime 无关的核心

- 状态：已接受（既有规范决策追记，不代表模块已实现）
- 记录日期：2026-11-07
- 依据：总规范原 §1–3、§5–6、§11 与 §23 的明确约束；原 §3.6 要求初期 In-Process Transport。
- 当前规则：[ARCHITECTURE.md](../../ARCHITECTURE.md)、[INTERFACE_CONTRACTS.md](../../INTERFACE_CONTRACTS.md)
- 替代关系：无前置 ADR。

## 背景

不同 Agent Runtime 的协议、能力、工具和权限模型不一致。Aether 的目标是统一管理与呈现，不是重写第三方执行逻辑。将 UI 绑定到具体 Runtime 或内部领域对象，会使接入新 Runtime、独立测试和未来多前端演进相互牵制。

## 决策

Frontend 的唯一业务入口是 Backend API Contract，DTO 与领域对象分离；Backend 不依赖 UI，能够无 UI 运行与测试。Core 定义领域规则及所需抽象接口，独立 Adapter 实现 Runtime 接入、能力发现及统一事件映射。

模块通过公开接口及显式依赖注入组合；运行时经函数表调用实现不授权源码依赖具体 Adapter。异步事件驱动业务变化，后台事件经 UI Queue 更新 UI，资源所有权与回调生命周期必须明确。

初期 Backend 使用进程内通信，保留逻辑架构边界；跨进程或网络传输按实际需求另行决策，不预建完整远程框架。

## 理由与替代方案

直接在 UI 调用 Runtime 或数据库可以减少初期接口代码，但违反独立测试和解耦目标。Core 直接绑定某个 Runtime 会把协议变化传播到业务核心。初期全面进程拆分增加序列化、部署、断连与安全成本，尚无必要需求支持。

采用公开契约、独立 Adapter 与进程内实现，保留所需边界而不预先承担远程通信复杂度。

## 影响与风险

需要维护 DTO 映射、能力差异、错误传播和异步生命周期；不能把所有 Runtime 强制压成相同能力。统一权限交互不意味着能够拦截第三方 Runtime 的全部内部操作，同进程分层也不是安全沙箱。

本记录不批准任何具体 UI/异步库、固定线程数量、沙箱机制、Runtime 协议版本或首个接入顺序。这些选择须以实际证据单独决策。未来替代现有边界时新增 ADR，明确影响及契约迁移，并同步当前规范。
