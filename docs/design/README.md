# Aether 项目概要设计

- 版本：0.1
- 范围：整个 Universal Agent Desktop，而非某个单独子系统。
- 状态：分层实施蓝图；已建立最小 C17/CMake 工程骨架并完成 Windows P1 smoke 验证，业务产品仍未实现。
- 文档约定：既有规范中的硬约束继续有效；本套文档的建议模块、操作名称、数据组织及方案不是冻结 API、数据库 Schema 或已批准选型。

## 1. 项目要交付什么

Aether 用一个桌面应用统一接入不同 Agent Runtime，使用户在工作区中选择 Runtime、创建会话、发送结构化消息、观察任务、处理权限请求并管理可用工具与配置。目标平台为 Windows、macOS、Linux，自研业务代码使用 ISO C17。

核心价值是统一管理与交互，不是重写 Codex、Claude Code、Pi、OpenCode、OMP、DSH 的执行逻辑，也不是强迫所有 Runtime 拥有相同功能。Aether Native Runtime 是另一个真实执行提供者，不能由 Mock 冒充。

完整项目包含 Runtime 管理、Workspace/Session/Message、任务状态、权限、MCP/Skills/Tools、配置和持久化、日志诊断、跨平台工程及实际桌面体验。IPC、多前端、编排、长期记忆、数据分析、插件与远端管理属于总规范后续演进阶段，不因此提前建设框架。

## 4. 系统组成与权威状态

| 层 | 系统角色 | 持有的状态 | 与相邻层协作 |
| --- | --- | --- | --- |
| Frontend | 展示与用户意图 | ViewModel、选择项、加载/错误/交互状态 | 只通过 Backend API/DTO/Event |
| Backend | 统一入口与用例协调 | 请求上下文、在途应用任务、订阅与事务协调状态 | 调用 Core 公开接口及注入端口，映射结果 |
| Core | 业务规则 | Workspace、Session、Message、权限等领域权威状态 | 定义接口，使用注入的 Runtime/存储等能力 |
| Adapters | 外部能力转换 | 协议连接、Runtime 实例关联、外部请求映射 | 实现 Provider，使用统一 IO 服务并发布标准事件 |
| Infrastructure | 技术资源实现 | 文件/连接/队列/日志输出等技术状态 | 实现所需公开端口，不拥有领域决策 |
| Platform | OS 差异隔离 | 系统句柄及平台资源 | 对上提供统一能力，不依赖业务或 UI |

应用入口是组合根：选择具体实现并注入依赖，组织启动/关闭；不成为第二套业务服务。源码依赖与运行时调用不同，Core 通过函数表调用 Adapter 不意味着可以引用 Adapter 实现头文件。

## 5. 用户可观察的完整使用链

1. 启动桌面应用，读取有效配置，显示 Runtime 可用性与权限控制能力。
2. 创建或选择工作区，检查目录和访问范围，选择实际可用 Runtime。
3. 创建会话，展示模型与能力；消息输入按能力支持文本、文件、图像或其他结构化内容。
4. 提交消息后区分受理与执行中，持续呈现消息增量、工具活动、权限请求与任务状态。
5. 用户允许或拒绝具体权限请求、取消任务；后台报告明确结果和资源清理情况。
6. 查询历史及配置；支持恢复的 Runtime 才恢复其会话，不把本地历史显示当作外部运行上下文已恢复。
7. 发生错误时用安全提示和诊断 ID 定位问题；通过 Backend 查看诊断，不能直接读业务或日志文件。
8. 正常退出或异常后再启动，遵循存储/恢复约定，不遗留无主进程、不重复执行副作用。

每一步的数据、错误和异步所有权必须落实到公开契约。首条链路跑通只是集成检查点，不等于多 Runtime、工具生态和完整桌面均完成。

## 6. 已定约束与未定选择

已定：C17、前后端分离、接口依赖与显式所有权、事件驱动、独立 Adapter、进程内 Backend 起步、统一权限与可追踪诊断。每个手写代码文件最多 500 行，超过 300 行审查职责；C 源码 80 列目标、100 列常规上限。

未定：UI 框架和版本、异步库/循环集成、线程数量、数据库与持久化细节、首个 Runtime 和协议版本、Native Runtime 的执行范围、权限继承与强制隔离、ID 编码与容量数值。技术候选不能作为默认批准清单；详见实施文档的决策门槛。

本套设计对存储组织、模块落位和任务顺序提供推荐，而不是虚构已有工程命令。具体接口与依赖选择确认后同步权威规范/ADR，再实现和实测。
