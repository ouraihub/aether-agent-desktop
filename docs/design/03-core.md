# 03 · Core：领域对象、规则与端口

## 1. 定位与阅读边界

Core 回答“对象是什么、关系是否成立、操作是否允许”，不负责 UI、协议解析或 OS 调用。
当前为设计阶段，本文的新增概念拆分、模块落位和操作名均为建议，不冻结结构体或 ABI。
规范依据为 [工作入口](../../AGENTS.md)、[架构规范](../ARCHITECTURE.md) §2、§6–8、
[接口契约](../INTERFACE_CONTRACTS.md) §5–11 及
[工程规范](../CODING_STANDARDS.md) §3、§6–7。
入口编排、请求终态和订阅见 [Backend](02-backend.md)，不在本层重复定义。
总阅读路径见 [总览](README.md)，全局选型与实施门槛见 [交付设计](06-delivery.md)。

## 2. 主对象与关联建议

下表中的描述/实例拆分用于防止身份混淆，是待评审建模建议，不表示规范已给出完整实体。
不为每个概念机械建立独立生命周期、Registry 或动态分配对象。

| 对象 | 建议表达的领域含义 | 关系与边界 |
| --- | --- | --- |
| Agent 描述 | 用户可选择的 Agent 配置或配置组合 | 引用 Runtime 选择及适用配置，不等同于 OS 进程 |
| Agent 运行实例 | 一次实际运行的 Agent 身份与状态（确有独立语义时） | 与 Runtime 实例、Session 的基数须确定；没有独立职责则不增设实体 |
| Runtime 描述 | Provider 类型、展示信息、版本及可发现能力的描述 | 描述可存在而尚无运行实例，不把类型名当连接 ID |
| Runtime 实例 | 一次启动或连接所形成的运行身份 | 可以是本地子进程、已有连接或远端连接；重连身份待定义 |
| Runtime Registry | 已登记 Provider/描述与运行实例的受控查找入口 | 登记不等于可用或有权限，不采用隐藏全局单例 |
| Workspace | 工作目录及项目、权限、Runtime、环境、工具、Skills 配置范围 | 一个 Workspace 可关联多个 Session，不等于 Session |
| Session | 持续交互的业务对象 | 保留 Session/Runtime/Workspace ID、时间、状态、模型与上下文关联 |
| Message | 会话中的结构化交互记录 | 保留 ID、Session、Role、内容块、时间、状态与 Metadata |
| Request 关联 | 一次应用操作与领域对象、外部请求的关联 | 应用请求由 Backend 拥有，不与 Message、Session 生命周期合并 |

规范中的 `runtime_id` 最终指描述还是实例、两者如何关联，须在接口发布前统一定义。
若拆出实例标识，应同步 DTO、事件及 Adapter 关联表，而非在不同模块赋予同名字段不同含义。
Session 在某一时刻绑定何种运行身份、是否允许迁移以及失联后的行为也须明确。
Workspace 与 Session 的一对多关系是既有要求；其余基数不能仅凭本表推定。

## 3. 状态唯一拥有者与不变量

| 状态类别 | 负责拥有和修改的边界 | 其他层的使用方式 |
| --- | --- | --- |
| Workspace/Session/Message 领域状态 | 对应 Core 模块 | Backend 通过公开操作修改、通过快照映射 DTO |
| Runtime 领域可用性及登记关系 | Core Runtime/Registry 模块 | 接收 Adapter 事实，经明确转换规则更新 |
| 协议连接、外部请求映射、读取缓冲区 | Adapter | 向 Core 报告归一化事实，不直接修改领域私有数据 |
| 应用请求受理、编排与最终交付 | Backend | Core 返回领域结果，不竞争同一应用请求终态 |
| 权限策略及有效授权的领域语义 | Core Permission | Backend 组织交互，执行端实施可实现的检查 |
| ViewModel 与显示状态 | Frontend | 只由 DTO/事件驱动，不反向成为领域事实来源 |

这里规定逻辑修改责任，不指定一个全局线程、内存池、锁方案或统一对象所有权模式。
每类可变状态还须明确执行域和同步规则；Registry 不能顺便成为全部对象的 Manager。

实施时至少维护以下不变量：

- Session 必须能定位有效的 Workspace 与明确的 Runtime 关联，未知 ID 不落到“当前对象”。
- Message 必须属于指定 Session；流式更新不能仅凭到达顺序附到最近一条消息。
- 能力支持、领域前置状态与权限允许分别成立，不能彼此替代。
- 状态变化只能由拥有者按已定义规则提交，外层 DTO 修改不得直接改变领域对象。
- 关闭、失败或 Runtime 不可用后的允许操作由契约规定，不借示意路径推断可恢复。
- 领域对象删除或关闭时必须处理仍被请求、内容块、授权或订阅引用的关系。

## 4. Message 内容块与流式归并

角色沿用 system、user、assistant、tool；内容至少考虑 Text、Image、File、
Tool Call、Tool Result、Structured Data，不将所有 Runtime 内容压成字符串。
每类块定义载荷与顺序；图像/文件采用内联数据、路径还是受控引用尚待决定。
文件可访问性与 Workspace 权限有关，拥有一个内容引用不等于获得任意路径读取权。
Tool Call 与 Tool Result 要有明确关联，Runtime 未提供充分关联信息时不能猜测配对。

Adapter 只把原始流转换成统一增量；Core 的消息拥有者按约定合并并更新领域状态。
必须确定增量针对哪个消息/块、追加还是替换、完成与中断后的内容是否保留。
未知块、不支持块、重复增量、迟到完成及协议中断均须有明确结果，不静默吞掉。
消息完成不自动等于应用请求成功、磁盘已保存或外部进程已退出。
持久化提交与应用完成交接由 [Backend](02-backend.md) 协调，不在消息模块另建事务入口。

## 5. 专题领域边界

| 模块 | Core 应表达的内容 | 外部实现或明确非目标 |
| --- | --- | --- |
| Permission | Allow/Deny/Ask/Inherit、作用域、操作关联、授权失效规则 | UI 确认由 Backend；执行检查由实际服务/Adapter；不承诺未知 Runtime 内部可拦截 |
| Tool/Registry | 工具描述、能力、权限需求、调用及结果语义、可管理生命周期 | 执行与审计 IO 在外部；登记 Runtime 自有工具不等于接管执行 |
| MCP | Server/Client 配置关系、发现结果及 Tool/Resource/Prompt 领域表示 | 连接、协议编解码及网络 IO 不进 Core，不在每个业务模块内置 Client |
| Skills | 元数据、作用域、启停及所需校验规则 | 存储加载独立于 Adapter，Runtime 特定配置映射由 Adapter 完成 |
| Configuration | 配置项语义、作用范围、生效条件及领域校验 | 文件/数据库/凭据存储由 Infrastructure；应用保存和反馈由 Backend |
| Memory | 将来长期记忆所需的领域语义 | 原 Phase 7；当前不建向量库、检索接口、摘要流水线或空模块 |
| Event | 领域事实和必要关联 | API 事件 DTO 由 Backend 映射；日志不是领域事件总线 |

会话消息历史与 Runtime 上下文关联不自动成为长期记忆系统。
工具生态详见 [Runtime 与工具](04-runtime-tools.md)；存储、安全执行与配置 IO 见
[Infrastructure/Platform](05-infrastructure-platform.md)。
配置继承不默认为权限继承；两者冲突规则须分别定义，不能用合并配置覆盖授权限制。

## 6. 公开操作、外部端口与数据所有权

Core 的公开面优先是不透明对象和领域操作，不公开可随意修改的内部结构。
建议按当前用例提供登记/查找 Runtime、创建/关闭 Session、验证/提交消息、
读取领域快照、评估权限及应用有效决定等操作；这些名称不构成已发布函数清单。
Runtime Provider 是真实多态边界，由 Adapter 实现生命周期、能力、会话、消息及事件交接。
需要持久化或读取外部资源时，按实际领域需求定义窄端口，不先设计通用 Repository 框架。
通用计时、日志、调度等技术接口不必全部归入 Core；Core 只依赖允许的公开抽象。
组合根注入所需 Provider、Registry 及其他依赖，领域模块不得自行构造全局服务。

| 跨边界资源 | 发布前必须明确 | 实施行为 |
| --- | --- | --- |
| 描述、能力与查询快照 | 创建者、可变性、有效期、更新或失效条件 | 调用方不能长期保存未声明有效的内部视图 |
| 请求内容及内容块 | 借用/复制/转移、失败时转移是否发生 | 异步处理前确保数据有效；分配失败不丢失原所有者责任 |
| Provider 函数表与 context | 谁持有、何时允许销毁、依赖寿命 | 调用期间有效，部分初始化失败仍可清理 |
| 领域结果、事件及错误 | 回调有效期、输出有效性、配套释放方式 | 跨队列显式复制或转移，不能引用临时协议缓冲区 |
| Registry 条目及 Runtime 实例 | 注销前置条件、查找结果寿命、在用引用处理 | 注销不能留下悬空 Session/请求关联 |

不得把以上待定项替换为“全项目统一深复制”或“全部引用计数”。
逐接口选择足够简单的方案；资源寿命、逻辑状态拥有者与线程执行域是三个不同问题。
`TraceContext` 在真实边界显式传递，不进入长期业务实体作为隐式“当前请求”。

## 7. 状态与关系待定义表

规范给出的 Session 正常路径和异常状态只是来源，不是完整状态转换表。
实施某个操作前，为相关对象补齐“前态、触发、条件、后态、副作用、事件、失败及重复行为”。

| 待定义项 | 实施所需输出 |
| --- | --- |
| Agent 描述/实例是否分别存在 | 独立身份的真实用例、与 Runtime/Session 的基数及关闭责任 |
| Runtime 描述/实例身份及 Registry | ID 作用域、重连/重启、重复登记、注销和能力失效规则 |
| Session 状态转换 | Active/Idle 往返、异常出口、关闭中调用及是否支持恢复 |
| Workspace 配置变化 | 对既有 Session 的生效时点、读取一致性和权限影响 |
| Message 状态与增量 | 内容块 Schema、归并规则、终止/异常后可见内容及未知类型行为 |
| 权限继承与授权生命周期 | 冲突规则、有效期、策略变更/取消/关闭后的失效与执行前复核 |
| 领域事件与 Query | 事实产生时点、快照一致性及持久化失败时的对外含义 |

具体状态表与契约经评审后才转为 C17 实现；不通过示意枚举冻结完整状态机。
全局容量、具体依赖、首 Runtime 和 Native 策略统一留在交付决策门槛。

## 8. 实施行为与本层验收

先定义当前用例的对象关系及端口，再实现唯一状态拥有者、规则与错误路径。
后续按 Workspace/Session、消息、Runtime/Registry、权限等真实职责拆文件，
遵守 300 行审查、500 行代码上限和 C 源码 80/100 列要求，不一次建立所有空目录。
以无 UI、无真实 Runtime 强依赖的领域测试覆盖关联错误、不合法转换、能力不支持、
授权失效、结构化消息和分配失败；Provider 测试替身必须明确标识，不能冒充真实接入。
与 Backend 验收请求结果和领域事实不冲突，与 Adapter 验收未知/迟到/退出事件的归属。
还应覆盖 Registry 注销、Session 关闭、部分初始化及外部依赖释放时的资源安全。
单条真实交互链路的验收见交付文档；通过它不表示 Tool/MCP/Skills 或完整产品已交付。
