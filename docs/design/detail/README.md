# Aether 分层详细设计

## 1. 用途和状态

本套文档细化**整个 Aether 项目**，不是单独日志或聊天功能。对应 [概要设计](../README.md)，增加对象字段、输入输出、状态表、处理步骤、失败分支、资源寿命、文件职责和可观察验收用例，方便AI按任务直接落实。

当前已建立最小C17/CMake工程骨架并完成Windows P1 smoke；业务产品仍未实现。**本套新增具体算法与模型均为可供评审的推荐设计，不是已经批准的公共API或已实现软件。** 现行规范保持强制；UI框架、Runtime版本、数据库、线程模型、容量和安全策略未因本文自动选定。读取 [AGENTS.md](../../../AGENTS.md) 后按任务选读，不每次整套加载。

## 3. 从详细设计到代码

1. 核对实际仓库与现有调用方，先复用而不是机械照文件建议重建。
2. 选定当前实施单元，列出依赖的D-*议题及本层合同；普通实现细节按最小方案执行，重大公开行为/安全/选型按规则确认。
3. 将已确认行为落实到正式接口说明/公开头文件，补齐类型、容量、错误、回调线程与释放配对。不要把草案类型或操作名当ABI直接复制。
4. 先实现领域和接口行为，再连外部IO与真实UI；每一步交付完整可运行路径，不写空函数和假成功。
5. 跑本层与跨层行为场景，记录实际输出、平台和缺口；维护不超过500行的手写代码文件及单一职责。
6. 同步调用方/测试/文档；已批准的详细语义由正式契约唯一维护，本文转为实现理由/算法说明，不长期保留两份冲突定义。

## 4. 本轮已经细化的设计取舍

推荐基线为：Backend单一请求终态拥有者；有界输入复制后受理；执行时重新校验；单调deadline与明确竞争顺序；Context与业务DTO分离；原子快照/订阅交接；有界队列失效后重新同步；退订异步确认后释放回调上下文。它们在00及相关层有具体算法，不再只是“需要考虑并发”。

存储推荐短事务且不跨网络锁定，执行成功与保存成功分别表达；权限推荐方案由Core文档统一维护，IO只执行已验证的授权；日志沿用现有六级和追踪合同，不控制业务结果。这些新增方案仍须对应D-*评审，尤其权限组合、请求竞争和持久化成功定义。

## 5. 尚不能凭文档完成的部分

第三方协议必须补充实际版本、官方资料及真实接入结果，不能推测厂商wire格式。UI/数据库/异步库选择须有平台与许可证证据。Native Runtime的模型执行范围需明确；P7的IPC、多前端、编排、长期记忆、数据分析、插件和远端管理沿既有路线，在实际启动对应功能时补充专门详细设计，不用未经需求确认的接口预建它们。

这不删除任何项目方向，也不把候选/未来功能写成已完成。当前设计交付覆盖已明确的桌面平台各层及其实施方法；运行验证仍是后续代码交付的必要条件。
