# Runtime 适配与工具生态概要设计

## 1. 定位与阅读入口

本层把不同 Runtime 的真实能力映射为 Aether 可管理的会话、消息、工具与权限交互，
不重新实现第三方 Agent，也不把所有 Runtime 压成虚假的共同能力。
当前只有规范；下文的模块落位、操作名和数据模型均为建议，不代表现有实现或稳定 ABI。

- 开发入口：[AGENTS](../../AGENTS.md)；职责与候选接入方向：[架构规范](../../ARCHITECTURE.md) §4、§6–7。
- Provider、事件、取消与权限约束：[接口契约](../../INTERFACE_CONTRACTS.md) §5–11、§13。
- C17、资源安全与依赖引入：[工程规范](../../CODING_STANDARDS.md) §3、§6–8；不在本文复制硬规则。
- 上游：[Backend](02-backend.md)、[Core](03-core.md)；下游：[基础设施与平台](05-infrastructure-platform.md)。
- 展示边界：[Frontend](01-frontend.md)；阅读路径：[总览](README.md)；决策与完整交付：[实施路线](06-delivery.md)。

## 2. 模块分工与接口交接

| 建议模块 | 本层职责与拥有的数据 | 交接边界 |
| --- | --- | --- |
| 各 Runtime Adapter | 版本识别、能力发现、配置转换、协议会话及外部 ID 映射 | 实现 Core 定义的 Provider，输出统一事件，不持有 UI 或 Backend 对象 |
| 可复用协议层 | 已实际采用协议的帧解析、编解码、握手及协议请求关联 | 向 Adapter 交付协议结果；通用管道与网络 IO 由 Infrastructure 提供 |
| MCP 接入服务 | Server 连接、Client 协议、发现结果与在途调用 | Core 定义领域及抽象；Backend 编排管理操作；IO 不进入 Core |
| Skills 加载边界 | 来源读取、内容加载与格式校验 | Core 管元数据、启用及作用域规则；Adapter 负责 Runtime 配置映射 |
| ToolRegistry 接入边界 | 将 Aether 工具与外部能力映射为统一描述 | Registry 的领域规则归 Core；具体执行器承接授权后的调用 |

建议落位遵循架构规范的 `adapters/runtime/`、`adapters/protocol/` 与相关 Infrastructure 模块。
每种 Runtime 保留独立适配职责，但只创建当前实际接入的实现，不批量生成空 Adapter。
协议层只复用已证明相同的协议语义，不混入某 Runtime 的会话规则、领域权限或 UI 展示。
首次接入可保留局部协议实现；出现真实复用需求再提取，不先建通用协议引擎或插件框架。

状态保持单一拥有者：Core 拥有领域状态，Backend 拥有应用请求协调，
Adapter 拥有外部连接与映射状态，Process Service 拥有进程和管道资源。
Adapter 报告观察结果，由 Core 状态拥有者应用变化；不能并行维护第二份权威 Session 状态。

## 3. 版本调查与 Provider 设计

接入前形成可复核的调查记录：Runtime 版本、平台、官方资料、实际接口及启动方式，
所需 Bridge 的来源、版本、维护责任、许可证和安全限制。
完整候选协议表只维护在 [架构规范](../../ARCHITECTURE.md) §7.1；候选不是支持声明。
优先标准协议或官方稳定接口；确需 CLI 时独立封装 stdout、stderr、退出码与清理，
不把易变终端文本当成稳定结构化协议，也不偷偷回退成另一种执行方式。

建议 Provider 按四组语义设计：初始化/启动/停止/关闭、描述与能力查询、
会话创建/关闭与消息提交/取消、事件订阅。具体签名、版本及 `shutdown` 与关闭阶段的
对应关系需先按接口契约评审，不直接复制示例函数表。
提交返回表达拒绝或受理；最终消息、失败或取消通过已定义的异步完成路径交付。
Backend 的 RequestContext 与业务 DTO 分离；所需 TraceContext 显式穿过 Provider 和 IO 回调。

建议能力报告关联实际 Runtime/协议版本、实例及适用会话条件，并记录调查或探测依据。
区分支持、不支持、未知和查询失败；明确报告何时失效、重新连接后何时重新确认。
Streaming、Cancellation、MCP、Skills 等维度按真实能力报告，不按产品名称推断。
能力存在不等于已授权；可选操作缺失须有可观察结果，不能返回空结果冒充成功。
各 Runtime 的差异保留在能力与适配中，不要求修改 Core 主体或 Frontend 名称分支。

## 4. 资源、外部标识与生命周期

受管本地 Runtime 由 Adapter 向 Process Service 提交经校验的可执行文件、参数列表、
工作目录和受控环境。Process Service 经 Platform 启动、读取、等待退出及释放句柄，
Adapter 不直接调用 OS 进程 API，不拼接任意 Shell 命令，不默认继承全部环境。
连接既有或远端 Runtime 时，不伪造本地进程；借用服务的连接关闭与服务终止分开。

| 资源 | 建议归属与释放交接 |
| --- | --- |
| 受管进程与管道 | Process Service 持有；Adapter 发起受允许的停止/终止，等待退出与异步关闭结果 |
| 既有服务与连接 | 服务所有权不转移；释放 Aether 自己创建的连接，不终止他人进程；借用句柄按借用契约归还 |
| 协议缓冲与外部 ID 表 | Adapter/协议实例持有；异步载荷复制或明确转移，不借用调用栈内存 |
| 共享 Process、日志等服务 | 由组合根注入；Adapter 不擅自销毁，服务寿命覆盖使用者 |
| 在途请求、订阅和回调上下文 | 分别声明终结者与释放时点；发起关闭不等于已无回调 |

建议映射键包含 Runtime 实例身份、连接/重启代次和外部请求 ID，
关联内部 Request、Session、Message/内容块、Tool Call 及必要 TraceContext。
外部 ID 不能直接充当全局 ID；同一外部值在不同 Runtime、会话或重启后复用不能串线。
重启或重新连接划分新代次，旧回调不能命中新请求；会话恢复只能依真实能力重新绑定，
不能因为外部 Session ID 相同就假定恢复成功。映射的保留时限与清除条件需契约化。

启动流程建议为：取得依赖与配置 → 建立资源 → 握手及能力确认 → 发布可用状态。
启动失败回滚已取得资源；关闭时停止接收，向请求协调者报告在途调用事实，停止事件生产与订阅，
等待 IO 关闭、清理映射及对象；应用请求终态由 Backend 协调者裁决。重复停止、部分初始化销毁与关闭中的回调须有定义。
不默认自动重连、重试或重放；这些动作可能再次产生副作用，须单独决策。

## 5. 流式消息、取消与故障

原始事件先校验版本、结构、大小和关联信息，再转换为统一内容块及领域事件。
流式增量关联确定的消息与内容块，Tool Call/Result 保留调用关联，
不能把全部输出拼成纯文本。原始协议对象不越过 Adapter 成为前端 DTO。
协议层拥有解析状态，Core 拥有消息状态；增量排序、重复片段和结束标记按契约处理。
未知事件不能静默解释为成功；无从关联的事件不得挂到“最近请求”。

取消依次经过 Backend 请求定位、Provider 能力检查和 Adapter 的真实取消操作。
取消受理不等于 Runtime 停止；不支持取消时明确报告，不以杀死共享进程冒充单请求取消。
超时、完成、取消和异常退出可能竞争，须由约定的状态拥有者裁决唯一可解释的终态；
已产生内容如何保留、迟到输出如何处理、取消是否影响同进程其他 Session 都需明确。
断连、非零退出、协议损坏和权限拒绝转换为统一错误及受影响请求状态，保留底层原因，
由 Backend 转换用户提示与诊断 ID，不能让请求永久显示运行中。
流量上限与背压交给 [实施路线](06-delivery.md) 决策；不得无限缓存或丢弃关键终态/权限事件。
追踪只做横切诊断，不解析日志驱动状态，也不向不支持的外部协议强塞追踪字段。

## 6. MCP 服务、工具执行与权限

建议 MCP 管理流程为：配置登记与校验 → 启动受管 Server 或连接既有 Server →
协商及发现 Tool/Resource/Prompt → 向上发布可用描述 → 调用 → 断开并使连接相关描述失效。
Server 配置与凭据存储由基础设施承担；启动仍经过 Process Service。
连接可用不等于工具已获授权；发现失败、版本不匹配和服务退出有独立可观察状态。
不默认发布 Aether 自身为 MCP Server，也不把 Client 实现散落到业务模块。

建议 ToolRegistry 描述至少区分工具来源、实际执行者、可调用能力及权限控制点：
Aether 本地执行器、Aether MCP Client、Runtime 原生工具是不同执行路径。
Registry 负责注册、查询、描述与调用路由，不因统一登记而获得外部工具执行权。
Aether 执行路径为：Backend 接收调用 → Core 解析工具与权限 → Ask 时关联用户响应 →
执行前核验有效授权和参数范围 → 执行器调用 → 统一结果/错误与审计事件。
授权关联具体 Workspace、Session、Runtime、Tool 与操作；取消、策略变化或关闭后的
迟到批准不得恢复已失效调用，调用结果也不能串到其他工具请求。

Runtime 原生权限请求仅在接口真实支持时映射并回送决定。
Runtime 内部自行调用的工具或 MCP 可登记展示已观察信息，但不能标成 Aether 已执行、
已授权或完整审计；不经 Aether 的内部操作无法仅凭统一权限模型拦截。
若工作流要求的强制限制无法实现，明确报告不满足，不静默降级为“受控”。

## 7. Skills 生命周期与 Native Runtime

建议 Skills 流程为：按已批准来源发现 → 读取元数据及版本 → 校验格式、依赖与内容边界 →
按作用域登记 → 用户启用 → Adapter 检查能力并映射配置 → 报告实际生效结果。
发现不等于启用，格式有效不等于可信；内容不得被当作 Aether 的权限授权或可执行命令。
加载与存储独立于 Runtime，Core 管启用/禁用和作用域，Adapter 只处理目标格式差异。
需明确名称冲突、版本切换、禁用、文件变化和配置失败时的行为，
以及当前 Session 是否受影响、是否需新建会话；不能仅保存设置就声称 Runtime 已加载。
工具、Skills 或 MCP 为 Runtime 自有时，只承诺其真实暴露的查询和配置能力。

Aether Native Runtime 是真实执行能力的产品方向，不是 Mock、固定回复或协议模拟器。
它同样实现 Provider、报告真实能力，并遵守工具执行、权限和资源边界；
其模型接入、执行循环与工具协作需要单独明确，不能为架构占位写空实现。
原路线的建议顺序不构成“Native 默认第一接入”；具体阶段、真实执行范围及先后顺序见实施决策，不得自行从项目范围删除。
Mock/Simulator 仅用于隔离测试，不能替代 Native 或第三方 Runtime 的真实验收。

## 8. 实施顺序、待明确问题与验收

新增 Adapter 按以下完整切片推进：版本能力调查 → 选择真实场景并评审 Provider/事件差异 →
注入 Process/IO 等依赖 → 完成配置、生命周期与映射 → 接通消息、取消与错误 →
补足能力报告和适用工具配置 → 契约测试与真实 Runtime 验证 → 更新兼容性记录。
单条真实端到端链路用于检验边界，不代替多 Runtime、工具生态与完整桌面产品的交付。

实施前需明确本层问题：首 Runtime 的确切版本与接口、能力报告有效期、外部 ID 作用域、
重启代次及映射清理、Provider 回调归属、取消终态、MCP 调用授权点、Skills 生效时机。
具体协议、依赖、线程、容量及 Native 策略统一送入 [实施路线](06-delivery.md) 的决策门槛。
不得借本层接入提前建立 Phase 7 的编排、长期记忆、高级 IPC 或通用插件空壳。

本层验收覆盖真实启动/连接、创建会话、消息及所支持的流式输出、取消和关闭，
并覆盖能力缺失、权限拒绝、异常退出、畸形输入、ID 冲突、重启迟到事件和借用资源不被误杀。
MCP 验证发现/调用/断连与实际执行权限；Skills 验证校验/启停/配置失败及真实生效。
Backend/Core 验证统一事件、状态与终态，Infrastructure 验证进程和句柄回收，
Frontend 只验证能力及结果呈现；真实环境按平台和版本报告，不以模拟通过冒充跨平台接入。
以上是后续实施验收要求，本文不声称已有实现或已经运行这些验证。
