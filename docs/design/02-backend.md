# 02 · Backend：应用入口与流程协调

## 1. 定位与阅读边界

Backend 把用户意图组织为可追踪、可取消且结果明确的应用操作；它不是另一套领域模型。
当前只有规范，以下模块落位和操作名均为建议，不代表已有实现或已发布 API/ABI。
领域对象、状态规则与端口见 [Core](03-core.md)，UI 交接见 [Frontend](01-frontend.md)。
实现须按 [工作入口](../../AGENTS.md)、[架构规范](../../ARCHITECTURE.md) §2–5、
[接口契约](../../INTERFACE_CONTRACTS.md) §2–4、§7–13 和
[工程规范](../../CODING_STANDARDS.md) §3–7 落实；此处不复制完整硬规则。
整体阅读路径见 [总览](README.md)，跨层实施与全局决策见 [交付设计](06-delivery.md)。

## 2. 模块分工与建议落位

| 模块建议 | 负责的工作 | 不承担的工作 |
| --- | --- | --- |
| `backend/api/` | Command/Query 入口、输入检查、版本及边界错误映射 | UI 事件处理、Runtime 协议解析 |
| `backend/transport/inproc/` | 进程内客户端到入口的调用与回调交接 | 预建 IPC、网络鉴权或通用传输框架 |
| `backend/services/` | 按用例编排领域操作、请求与事务协调 | 重写领域状态机、直接依赖具体 Adapter |
| DTO 映射单元 | 业务 DTO 与 Core 输入、快照、结果的转换 | 公开 Core 指针或第三方结构体 |
| 请求与事件协调单元 | 在途请求、终态交付、订阅与关闭协调 | 将日志当业务事件或复制 Session 状态 |

这些是职责划分，不要求每格立刻成为独立组件或文件。
公开契约建议落在 `contracts/api/`、`contracts/dto/`、`contracts/events/`；
服务内部辅助接口不为跨文件调用而升级成公共 API。
后续 C17 实现按真实职责拆分：超过 300 行审查，最多 500 行，80 列目标、100 列上限。

## 3. API 形态与 DTO 交接

| 交互 | 建议用例 | 结果语义 |
| --- | --- | --- |
| Command | 创建会话、发送内容、取消请求、响应权限、保存配置 | 区分入口拒绝、受理与后台业务完成 |
| Query | 列出 Runtime、读取会话及消息、查询配置和诊断 | 返回受控 DTO；明确快照时点与有效期 |
| Event | 消息增量、状态变化、权限请求、请求完成 | 表达已发生的事实，不替代命令响应 |

同进程不省略契约边界，但也不要求先序列化再反序列化。
入口先校验版本、必填项、长度、请求总量与可空规则，再映射到领域输入。
Core 继续检查对象关联、不变量与操作前置状态；两层校验目的不同。
Query 不旁路到领域私有内存或数据库，调用者不得获得内部可变对象。
消息 DTO 保留结构化内容块；能力不支持的输入返回明确结果，不静默降为纯文本。
失败响应映射稳定错误码、安全提示与诊断 ID，不透传 SQL、命令、敏感路径或协议正文。

## 4. 请求上下文与权限交接

业务 DTO 只携带业务参数；独立 `RequestContext` 参数或外层信封承载请求元数据。
其具体表示待发布契约确定，包括必要的请求关联、已验证调用者信息与 `TraceContext`。
不为了未来多用户创建通用 Actor 框架，也不把 Trace ID 当身份或授权凭证。
可信入口创建或验证上下文，后续服务显式传播；跨队列保留有效值而非入口栈地址。
独立用户操作建立 root，下层真实边界建立 child span；业务请求 ID 与 trace 各司其职。

权限规则由 Core 决策，Backend 协调 Ask 请求、界面答复与在途操作的关联。
执行服务或 Adapter 在实际副作用边界实施可实现的检查，不只在入口检查一次。
响应权限前核对目标操作及 Workspace/Session/Runtime/Tool 范围和请求有效性。
取消、会话关闭、Runtime 退出、策略改变后的迟到答复不得使失效操作继续执行。
Runtime 自行执行且未经过 Aether 的操作不在此保证内，缺口须随能力明确展示。
权限执行与协议交接详见 [Runtime 与工具](04-runtime-tools.md)。

## 5. 应用服务目录

| 建议服务组 | 编排职责与上下游 |
| --- | --- |
| Agent/Runtime 服务 | 查询描述与能力；经 Core 发起实例运行操作，接收归一化结果 |
| Workspace/Session 服务 | 打开或管理工作区、创建及关闭会话，协调所需配置与存储 |
| Message/Request 服务 | 提交内容、关联请求及消息，协调流式结果、取消和终态交付 |
| Permission/Tool 服务 | 组织授权交互与工具调用用例，不接管 Runtime 未开放的内部行为 |
| MCP/Skills 服务 | 管理用户可见配置与操作，调用对应领域接口，不嵌入协议客户端 |
| Configuration 服务 | 校验变更、解析生效范围、协调保存和生效反馈 |
| Diagnostics 服务 | 受控查询诊断、返回可复制 ID 与采集状态，不直接暴露日志路径 |

按实际用例实现服务，不为表中每项提前生成空 Manager；配置与诊断可以先作为窄接口。
Backend 拥有应用请求上下文和编排进度；Session、Message、权限策略由 Core 唯一拥有。
Adapter 的连接状态与 Infrastructure 的 IO 状态只以事实反馈，不成为 Backend 的领域副本。

## 6. 一次发送请求的实施路径

1. Frontend 通过 inproc 提交内容 DTO 与请求上下文；入口完成边界检查。
2. 服务请求 Core 检查 Session 关联、可用能力、消息内容与适用权限。
3. 在越过异步边界前完成输入复制或明确转移，记录请求关联与清理责任。
4. 服务按该用例声明的受理条件返回；受理不表示消息已完成或已持久化。
5. Core 经 Provider 调用 Adapter；原始响应由 Adapter 归一化后交给状态拥有者。
6. Core 更新领域状态，Backend 映射事件 DTO，经订阅交给 Frontend 的 UI Queue。
7. 请求协调者按已定义的竞争规则裁决完成、失败、超时或取消并交付结果。
8. 底层工作若仍需停止或关闭，继续履行资源清理责任，不能随用户等待结束而遗忘。

这条链路是分层验证入口，不代表完整桌面产品或全部 Runtime 已完成。

## 7. 异步请求、订阅与关闭

请求协调者是应用请求终态的唯一裁决入口；Core 不另设一份相互竞争的应用请求状态机。
领域操作结果、底层任务停止与 UI 等待结束是不同事实，须通过关联标识交接。
不在本概要固定完整状态枚举、裁决算法或通知次数；先完成下表再实现相关接口。

| 待定义契约 | 实施时必须形成的行为 |
| --- | --- |
| 请求 ID 作用域及保留期、重复提交语义 | 多 Runtime/多 Session 不串请求；不暗设自动重试或幂等 |
| 受理条件、终态集合与通知次数 | 拒绝、在途、最终结果可区分；受理后失败不会变成成功 |
| 完成/超时/取消竞争与迟到事件 | 单一裁决结果，迟到回调按规则处理且不重复终结 span |
| 超时起点、取消能力与清理归属 | 明示等待结束后底层是否继续，取消反馈不伪称进程已停 |
| 事件顺序作用域、Query 一致性 | 明确增量、完成、错误、退出及快照的关系，不假设全局有序 |
| 订阅句柄与回调执行域 | 规定建立失败、重复退订、重入、回调内退订及释放时点 |
| 退订返回后的排队/执行中回调 | 调用方知道何时可释放上下文，销毁后不访问已释放对象 |
| 慢消费者与关键事件交付 | 按已批准容量及背压策略产生可观察结果，不静默丢关键状态 |

关闭时协调停止接收新工作、处理在途操作、停止事件生产、解除订阅及关闭资源。
具体顺序需覆盖依赖关系和仍在执行的回调，最后才释放其引用对象；不得阻塞 UI 等待。
部分初始化及启动失败同样进入可清理路径，不能依赖所有服务已成功启动。

## 8. 应用事务与持久化失败

应用服务是用例事务的协调入口；Core 保证领域合法性，存储实现只执行约定 IO。
数据库事务不能原子回滚外部 Runtime 已执行的工作，不建立虚假的跨 Runtime 全局事务。
每个涉及存储的用例先说明：需要保存哪些事实、保存与内存更新/外部副作用的顺序、
成功响应及事件意味着“已执行”还是“已持久化”，以及失败后重启能恢复什么。

| 失败位置 | 必须明确的处理 |
| --- | --- |
| 受理前保存或准备失败 | 返回失败并清理临时资源，不发布业务完成 |
| 外部操作完成但保存失败 | 分别报告执行事实与保存失败，不假称外部副作用已回滚 |
| 内存变化与存储提交不一致 | 按用例选择已评审的恢复/撤回或显式受限状态，不静默分叉 |
| 配置保存失败 | 区分有效值、用户偏好与已保存值，不承诺重启恢复 |

具体提交时点、恢复方案和存储选型交由 [持久化与基础设施](05-infrastructure-platform.md)
及 [交付决策](06-delivery.md) 落实；不预建事件溯源、事务框架或自动补偿引擎。

## 9. 诊断配置服务与本层验收

诊断 Query 支持 trace 精确检索和 operation/layer/component/level 筛选，返回时间与耗时。
须限制查询数量、检查访问范围，明确被过滤、轮转或丢失时的信息，避免递归诊断日志。
配置服务向日志设施传递有效级别；临时覆盖、持久化偏好及来源分别呈现。
级别优先级沿用工程规范，保存失败与“保存成功但仍被临时覆盖”给出不同反馈。
日志仅为横切诊断，不决定业务成功、不承担事务提交或事件投递保证。

实施前还需与上下游明确每项 DTO/错误/事件的版本、字段容量、内存有效期及释放配对；
不得以“统一复制”或“统一引用计数”替代逐接口所有权契约。
本层验收应覆盖无 UI 调用、DTO 隔离、请求竞争、退订/关闭回调、权限迟到响应、
持久化失败可见性及诊断访问边界；全局选型、容量与跨层真实场景由交付文档统一管理。
