# Aether 项目任务看板

## 1. 当前基线与使用入口

当前已有C17/CMake、Foundation/Core Runtime Registry、同步Backend生命周期/本地请求记录及Platform基础；这些不是已完成业务产品。任务状态以阶段表为准，调查和设计不等于选型批准或产品验收；本看板涵盖P1–P6与P7路线。

先读 [AGENTS.md](../../AGENTS.md)、[概要](../design/README.md)、[详细设计](../design/detail/README.md)，再从本清单选择任务。设计文档定义“如何实现”，任务表定义“还需要交付什么、当前到哪一步”；任务描述不能覆盖安全或公共契约。

ENG-04回归已修复，DEC-05请求事件语义已收敛；DEC-07/08/09/10仍待确认，DEC-11硬依赖未齐只可提前调查，ENG-05不绕过容量前置。Pi/OMP作为参考不意味着任意依赖、数值或安全策略自动批准。证据见[执行记录](EXECUTION_LOG.md)。

## 3. 状态及修改规则

| 状态 | 含义 | 允许转移/证据 |
| --- | --- | --- |
| 未开始 | 尚未认领；依赖未满足不自动叫阻塞 | 依赖满足且有负责人后转进行中 |
| 进行中 | 当前有人负责完整任务范围 | 完成实现转待验证；遇明确外部条件转阻塞；重大取舍转待确认 |
| 待确认 | 调查/方案已就绪，但缺少必须的项目决定 | 记录问题、备选、建议和影响；得到真实确认后继续，不自行批准 |
| 阻塞 | 存在具体且当前不可解决的环境/依赖问题 | 记录尝试、缺失条件、解除办法和责任；解除后重新选择进行中 |
| 待验证 | 实现已接通但运行/平台/真实协议证据尚不齐 | 运行对应场景；发现缺陷回进行中，缺外部条件转阻塞 |
| 已完成 | 整项交付与适用验收均满足 | 必须有执行记录/证据及审查结论，不能仅有代码或设计 |

不设置“默认跳过”“自动取消”状态。范围确需变化，先获得用户确认，记录原任务及调整原因；保留历史，重写依赖/验收和阶段出口，不通过删除任务掩盖未完成工作。已完成任务发现回归可回到进行中，并保留原验证和回归记录。

表格状态可直接修改跟进；当期负责人、开始/更新日期、分支/提交和证据只放 [执行记录](EXECUTION_LOG.md)，避免每张表膨胀。任务认领前检查最新记录，不能两个AI同时修改同一任务或共享接口而不设集成者。

## 4. 任务就绪与依赖

- “硬依赖”列只引用本任务系统ID。依赖均已完成才可开始实现；任务还要满足设计要求的批准/平台/资料条件。
- 依赖“无”仅表示没有任务ID前置，不免除阅读、授权和安全约束。
- 有关资料可提前调查，但不得将提前调查当作依赖尚未完成的实现任务已完成。
- 依赖过粗阻碍独立工作时，先正式拆分该前置：给稳定子ID、明确输出/验收、更新消费者依赖并保留聚合出口；不得口头绕过。
- 优先选择依赖满足、影响当前阶段出口的任务；文件次序不是严格执行次序，首Runtime不按表格名称排序自动决定。
- 公共状态/DTO/错误/权限合同指定一个维护者。不同Adapter或独立页面可并行，但每个子任务有文件范围和接口交接；变更共享合同先通知消费者并同步。

本系统不记录虚构工期或自动百分比。进度按已完成任务和阶段出口观察；不同粒度任务的数量不能直接当作工作量比例。

## 5. 每项任务的完成定义

1. 任务交付物全部存在且连通到真实调用方，没有空函数、假成功、未接线按钮或Mock冒充正式能力。
2. 受影响接口、全部调用方、数据/权限/线程和所有权合同同步；不得保留冲突的双实现或兼容别名掩盖问题。
3. 执行任务对应的设计用例，以及适用 [INT跨层场景](../design/detail/08-implementation-validation.md)。编译/单测不是唯一证明：UI用实际窗口，Adapter用真实版本，基础IO用真实可控进程/服务。
4. 覆盖错误、边界、取消/超时、关闭和清理的适用路径；测试使用隔离数据和合成秘密，不访问开发者真实凭据。
5. 运行适用构建、静态/格式、测试、资源检查；检查每个手写代码文件500行上限、300行职责审查、C行宽和例外。
6. 在执行记录中给出实际平台/命令或操作/结果/证据路径、未验证范围和审查结论；没有运行不能写通过。
7. 必要设计/使用说明/兼容性清单更新，临时试验清理。决策任务以确认记录和选型证据验收，不假称功能已实现。

某平台或真实Runtime未验证时，只能完成明确不要求该证据的局部任务；目标任务/发布出口继续待验证或阻塞，不能默认缩范围。

## 6. AI执行步骤

1. 读取入口、任务所在阶段文件及最新执行记录，查实际仓库变化；选择一个就绪任务或接口明确的独立任务组。
2. 更新状态为进行中，追加认领记录：负责人、文件范围、依赖核对、设计章节、验收用例和实际可用验证方式。
3. 说明需求/根因（如适用）、接口影响、状态/资源/权限边界及步骤，再实现；复杂任务可拆子项，但聚合任务须等全部子项及集成通过。
4. 真实运行、观察结果；出现新阻塞或重大决策即时记录，继续推进其他无依赖冲突的可达任务，不伪造通过。
5. 更新证据和交接记录后再将任务改为已完成；最后报告任务ID、交付内容、实际验证、遗留项和下一就绪任务。

可直接给AI的指令：

> 从 docs/tasks/README.md 选择依赖已满足的任务，优先当前阶段出口。先核实状态和实际代码，再读取该任务设计、认领并记录范围，按交付物和验收完成真实行为。同步任务状态与执行证据，不自批重大设计、不把编译或Mock当产品完成、不删减任务。完成后报告ID、验证结果和下一任务；阻塞时写出具体缺失与解除条件。

## 7. 追踪和审查约定

- 任务表拥有当前状态；执行记录保留历次事实；设计拥有行为定义；ADR保留重大决策理由。四者不重复维护同一事实。
- 新发现缺陷/遗漏用 `FIX-*` 或对应阶段稳定子ID登记，关联原任务和失败场景，纳入依赖与阶段出口；不能只写聊天中“后续再做”。
- 大任务分解采用如 `RUN-02-A` 的稳定子ID，所有子任务都有完整状态/依赖/交付/验收；父任务继续作为集成验收，不能复用或重排已有ID。
- 路线任务EVO开始时必须进一步拆分实际范围；本清单保留方向和完成门槛，不预先批准未知功能方案。
- 定期核对任务依赖无环、ID/链接有效、状态与证据一致，重点检查“已完成但无运行证据”“依赖未完成却已完成”“模拟当真实”等情况。
